# Qualified compatibility fallback

The current old production image requires paid SaaS, external malware scanning and KMS-only artifact configuration. Do not turn those services on or label its failed readiness probe as passing to make it a rollback target.

Normal releases still use the incumbent immutable image. A separately prepared internal compatibility fallback may be selected only through `EOS_COMPATIBILITY_ROLLBACK_MANIFEST_PATH`, which is local-only and never staged to Fly. Both recovery/payment and general integration provider effects must be explicitly disabled for this bounded preparation mode. The selector runs before the normal release evidence gate, image build, migrations and secret staging. It does not replace those gates or the public/authenticated smoke checks after rollback.

The secret-free `eos.compatibility-rollback.v1` manifest binds the application, environment, exact new release, incumbent image/subject, fallback image/subject, source base, qualification/security run IDs, migration target, isolated-runtime receipts and explicit operator approval. Every runtime proof must be passed, have an evidence reference and be less than 24 hours old. Public readiness must actually pass; a 503 is not accepted. Both the fallback and the new release must descend from the reviewed source base. Only the separately reviewed Stripe-health compatibility change and its test/documentation may differ from that base. The fallback's CI workflow blobs must match the canonical workflows exactly; neither tests nor security gates may be disabled. Run IDs are checked against GitHub's actual conclusion, repository, workflow path and source commit. Docker must hold the exact Linux/amd64 image digest with a matching source revision label.

Required rehearsal proofs: runtime readiness, public smoke, authenticated role/tenant isolation, migration compatibility, disabled EOS payment effects, disabled public paid SaaS and disabled untrusted uploads. Source tests and configuration-presence checks alone do not satisfy these proofs. A prepared image is not a verified fallback until its actual runtime and access checks pass. Production promotion still requires a separate exact-release approval and fresh signed-in smoke.

The compatibility fallback retains shared security fixes and intentionally disables only the new Stripe health HTTP probe. This is a bounded fallback, not protection against every defect in shared application code. Record this limitation in the approval. No merchant account is deleted, no Stripe object is activated and no payment action is authorized by fallback selection.

If configured, the final deployment receipt records the incumbent image, chosen rollback image and manifest SHA-256 separately. Without a complete approved manifest, preparation must stop before any production mutation. Never populate missing receipts or approvals with synthetic passing values.

Release archives explicitly disable Git's Windows CRLF conversion. The Linux entrypoint and ClamAV configuration must retain their committed LF bytes; otherwise a locally packaged build fails even when the same commit passes Linux CI. Fallback image preparation must use the same archive setting.
