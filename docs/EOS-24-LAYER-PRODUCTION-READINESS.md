# EntrepreneurOS 24-Layer Production Readiness

## Decision boundary

EntrepreneurOS has three distinct states:

1. **Current overlay implementation:** EOS provides its own tenant-scoped work, approvals, hierarchy, communication, audit, support, lifecycle, billing, analytics-consent, and integration adapter surfaces while remaining standalone-safe. UMH is an optional signed projection/control-plane integration, not EOS's database or browser authority.
2. **Required public SaaS MVP:** the overlay is publicly operable only after every layer below has current production evidence and `GET /api/platform/readiness` returns `ready: true`. A passing build, a healthy URL, or working development providers is insufficient.
3. **Native EOS end state:** the same role-aware organization model, EA-mediated founder communication, advisor portfolio, hierarchical company communication, approvals, evidence, and universal layout become native EOS capabilities rather than an overlay assembled around external reference and execution providers.

Status meanings:

- **Repository-qualified:** implementation and automated evidence exist in source control.
- **Partial:** implementation exists, but production configuration, drills, approval, or live evidence is missing.
- **External gate:** completion requires a production account, provider authorization, professional approval, named human owner, or production exercise and cannot be manufactured by code.

## Layer matrix

The front-end qualification includes an interactive Portfolio Map: only visibility-filtered seats are selectable, and each selection exposes accountability context plus real organization, work-room, and assistant actions inside the active role's existing surface grants.

The same role policy now governs actual entry and navigation. Active members can return through a minimal portfolio/organization selector without receiving owner or founder-private fields. Rendered journeys cover founder, portfolio executive, Company CEO, functional executive, manager, individual contributor, and external collaborator; verify role-filtered navigation, search, settings, work visibility, decision access, communication, and hidden-route recovery; and prove one principal can switch between two organizations with a different role in each. The individual-contributor journey is also verified at 390×844.

Repository-qualified team administration includes accepted-member lifecycle controls, organization invitation policy, a distinct-human allowance across owned companies and pending invitations, and portfolio-wide executive access that materializes into current and future portfolio organizations. SAML SSO, SCIM, and verified domain ownership remain end-state identity capabilities rather than claims of this overlay.

First-run acceptance begins from an empty founder account and completes portfolio creation, the full organization setup wizard, founder-seat resolution, the chosen Executive Assistant identity, and entry into the role-aware Home workspace. This keeps onboarding inside the same rendered usability gate as returning-member access.

Work Room provides the full assigned-work lifecycle to seats without Operations authority: selection, start/resume, exact evidence capture, review submission, completion gating, scoped assistant help, and a standalone-safe provider fallback that never points the user to a hidden surface.

The Settings experience also includes an administrator-only production workspace. It turns the matrix below into direct, authorized actions for exact control evidence, vendor review, service ownership, and signed alert testing; ordinary user roles cannot discover or invoke those controls.

## Current promotion blockers

The repository-controlled implementation is materially ahead of the currently deployed public pilot, but public SaaS promotion is intentionally blocked by current evidence. `npm run inventory:production` captures the repeatable read-only technical observation as a private ignored receipt plus SHA-256 sidecar. Its exact-merge 2026-08-26 run (`9a31b565d8dfac104e3fbcb3b15cd0fd282cf91c759ffddf2371bae0b35aaea0`) reports 17 named technical gaps against merge `b857f7d7f112e7e27a552698d67061c047fb5816` and the current 112-migration target, including the stale release subject and machine policy, incomplete production secret custody, missing live provider capabilities, the `neondb`/`eos_db` vault mismatch, and the production migration gap. This inventory is evidence of observed state, not evidence that the controls or the separate professional, operational, and field gates are complete.
