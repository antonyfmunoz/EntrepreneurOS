       ```typescript
       export const QUESTION_SEQUENCE = [
         "vision",       // What is this product? Who is it for? What problem does it solve?
         "user-flows",   // What are the 3-5 core things a user does? Walk me through each.
         "pages",        // What pages/screens do those flows require? List them.
         "page-detail",  // For each page: what components, data, auth level?
         "implied",      // Review: what requirements are implied but not stated? (errors, empty states, auth gates, loading)
       ] as const;
       export type QuestionStage = typeof QUESTION_SEQUENCE[number];
       ```

    2. Define and export the `CollaborativeState` interface:
       ```typescript
       export interface CollaborativeState {
         stage: QuestionStage;
         stageIndex: number;
         messages: Array<{ role: "user" | "assistant"; content: string }>;
         references: string[];  // URLs, screenshots, "make it like X" references (D-08)
         partialSpec: Partial<SpecOutput> | null;
         complete: boolean;
       }
       ```

    3. Export `function createInitialState(): CollaborativeState` — returns state with stage "vision", stageIndex 0, empty messages/references, null partialSpec, complete false.

    4. Export `function buildSystemPromptForStage(stage: QuestionStage, priorContext: string): string` — returns a system prompt for Claude that:
       - For "vision": asks about the product, target audience, core problem solved, revenue model
       - For "user-flows": asks user to describe 3-5 core user journeys step by step
       - For "pages": derives page list from user flows, asks for confirmation/additions
       - For "page-detail": iterates each page asking for components, data needs, auth level, layout preferences
       - For "implied": reviews all gathered info and identifies auth gates, error states, loading states, empty states, 404 handling, layout shell pages
       - Each prompt includes `priorContext` (serialized prior conversation summary) so Claude has full context
       - Each prompt instructs Claude to accept references at any point per D-08

    5. Export `function isFlowComplete(state: CollaborativeState): boolean` — returns true when stageIndex >= QUESTION_SEQUENCE.length and partialSpec is populated.

    6. Export `async function extractSpecFromConversation(messages: Array<{ role: "user" | "assistant"; content: string }>): Promise<SpecOutput>` that:
       - Sends the full conversation history to Claude with a system prompt instructing it to extract a complete SpecOutput JSON
       - Uses the same Anthropic SDK pattern as restructure-spec.ts
       - Validates with SpecOutputSchema.parse()
       - This is called at the end of the collaborative flow to produce the final output

    **Important:** This module defines types, state management, and prompt construction. The actual multi-turn conversation loop is driven by the SKILL.md (which instructs Claude Code to iterate). The module provides the building blocks; the skill orchestrates the interaction.

    **# saas-dev:spec-parser**

    Ingests a product spec (pasted or created collaboratively) and produces a validated `SpecOutput` — a structured `PageSpec[]` with composable layers for downstream phases.

    **## Input Paths**

    1. **Paste path (SPEC-01):** User provides raw spec text (any format: markdown, plain text, Notion export, bullet list). System parses and restructures into PageSpec[].
       - Call `parseSpec(rawInput)` from `lib/spec-parser/parse-spec.ts`
       - Returns validated SpecOutput

    2. **Collaborate path (SPEC-02):** User has no spec. System guides through domain-first questioning.
       - Import `createInitialState`, `buildSystemPromptForStage`, `isFlowComplete`, `extractSpecFromConversation`, `QUESTION_SEQUENCE` from `lib/spec-parser/collaborative-flow.ts`
       - Initialize state with `createInitialState()`
       - For each stage in QUESTION_SEQUENCE:
         - Build system prompt with `buildSystemPromptForStage(stage, priorContext)`
         - Ask the user the stage-appropriate questions
         - Record user responses in state.messages
         - Accept references (URLs, screenshots, "make it like X") at any point (D-08)
       - After all stages: call `extractSpecFromConversation(state.messages)` to produce SpecOutput

    **## Post-Processing Pipeline**

    After either input path produces an initial SpecOutput:

    1. **Chunking check (D-24/D-25):** If `output.pages.length > 25`, call `chunkSpecByDomain(pages)` from `lib/spec-parser/chunk-spec.ts`, restructure each chunk separately, then merge.

    2. **Deduplication (D-20/D-21/D-22):** Call `deduplicateComponents(output.sharedComponents, output.pages)` from `lib/spec-parser/deduplicate-components.ts`. Show user the merges: "I merged these descriptions into one shared component: `ComponentName`." User confirms or splits.

    3. **Backend spec derivation (D-09/D-10):** Call `deriveBackendSpec(output.pages)` from `lib/spec-parser/derive-backend-spec.ts`. Auto-generation always runs when UI spec exists. If user also pastes a backend spec, show derived vs pasted and let user reconcile.

    4. **Backend-only concerns (D-12):** After auto-derivation, ask user: "Are there backend-only concerns not visible from the UI? (webhooks, cron jobs, third-party integrations, background tasks)" Append overrides to backendSpec.

    **## Confirmation Gate (D-03, D-04)**

    Before persisting ANYTHING to Neon:
    - Display the full restructured spec to the user
    - Mark each item as EXPLICIT (from user input) or INFERRED (added by AI) — use the `inferred` flag on each spec item
    - Show the suggested generation order (D-15)
    - Show shared components with their deduplication merges (D-22)
    - Show the derived backend spec
    - User options: "approve", "edit [page name]", or "redo" to re-interpret from scratch
    - On "edit": apply surgical edit (D-16), bump specVersion, re-show only changed pages
    - On "approve": persist to Neon pipeline_pages table

    **## Persistence**

    After user confirms:
    - Create pipeline_run row with phase="spec", status="complete"
    - For each page in SpecOutput.pages: insert pipeline_pages row with output=JSON.stringify(page), status="complete"
    - Store SpecOutput as the phase output for the orchestrator to hand off to Phase 3

    **## Spec Editing (D-16/D-17/D-18/D-19)**

    When user requests a spec edit after initial confirmation:
    - Accept page name or route to edit
    - Re-parse only that page's spec
    - Bump specVersion on the edited page
    - Flag dependent pages for review (D-17)
    - Show confirmation gate for affected pages only
    - Update pipeline_pages status to "spec-changed" for the edited page
    - Pages with no relationship to the change are untouched (D-18)

    **## Contracts**

    - Input: raw text (any format) OR collaborative conversation
    - Output: `SpecOutput` from `shared/spec-schema.ts` — validated by `SpecOutputSchema.parse()`
    - Layers: PageSpecCore (all phases), PageSpecUI (Phase 3-4), PageSpecData (Phase 5), PageSpecAnalytics (Phase 6)
    - Composition: Downstream phases use `PageSpecCore.merge(PageSpecUI)` etc. to get only their fields

    **## Dependencies**

    - `lib/spec-parser/parse-spec.ts` — paste path entry point
    - `lib/spec-parser/restructure-spec.ts` — AI restructuring engine
    - `lib/spec-parser/collaborative-flow.ts` — guided creation state machine
    - `lib/spec-parser/derive-backend-spec.ts` — backend spec auto-derivation
    - `lib/spec-parser/deduplicate-components.ts` — shared component dedup
    - `lib/spec-parser/chunk-spec.ts` — large spec chunking
    - `shared/spec-schema.ts` — all Zod contracts
