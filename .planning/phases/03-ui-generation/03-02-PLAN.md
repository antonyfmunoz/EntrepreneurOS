<objective>
Implement Claude-based design token extraction from Stitch HTML output and component pattern conflict detection.

Purpose: After a page is approved, the system must extract design tokens (colors, typography, spacing) and component patterns (card styles, button variants, nav layouts) from the generated HTML, then check new patterns against established ones for conflicts. This is the design memory write path that enables visual consistency across pages (UIGEN-02, UIGEN-05).

Output: `lib/ui-generator/extract-tokens.ts` and `lib/ui-generator/conflict-detector.ts` with full test coverage (Claude API mocked in tests).

```typescript
export function extractJsonFromResponse(text: string): unknown {
  const fencePattern = /^```(?:json)?\s*\n?([\s\S]*?)\n?```\s*$/;
  const match = text.trim().match(fencePattern);
  const jsonText = match ? match[1] : text.trim();
  return JSON.parse(jsonText);
}
```

  <action>
    Create `lib/ui-generator/conflict-detector.ts` with one exported function:

    ```typescript
    import type { ConflictDetectionResult } from "./types.js";

    interface ExistingPattern {
      name: string;
      variant?: string | null;
      propsShape?: string | null;
      usageContext?: string | null;
      shadcnComponent?: string | null;
    }

    interface NewPattern {
      name: string;
      variant?: string;
      propsShape?: string;
      usageContext?: string;
      shadcnComponent?: string;
    }

    export function detectPatternConflicts(
      existingPatterns: ExistingPattern[],
      newPatterns: NewPattern[]
    ): ConflictDetectionResult
    ```

    Implementation per D-08 and Pitfall 5 (semantic comparison, not pixel-level):

    1. For each `newPattern`, find matching existing patterns by normalized name (lowercase, trim).
    2. If no match found, skip — new pattern, no conflict.
    3. If match found, compare semantic fields:
       a. Compare `usageContext` — if both defined and significantly different (not substring match), flag conflict.
       b. Compare `shadcnComponent` — if both defined and different, flag conflict.
       c. Compare `propsShape` — if both defined and different, flag conflict.
    4. For each conflict, generate a recommendation string:
       - If shadcnComponent differs: `"Pattern '${name}' uses ${newShadcn} but established pattern uses ${existingShadcn}. Consider: unify to existing, keep both as named variants, or override."`
       - If usageContext differs: `"Pattern '${name}' has different usage context. New: '${newCtx}', Established: '${existingCtx}'. Consider if these are the same component or distinct variants."`
    5. If variant field differs but name matches, this is intentionally a different variant — NOT a conflict.
    6. Return `{ hasConflicts: conflicts.length > 0, conflicts }`.

    The comparison is deliberately lenient per Pitfall 5 — only flag when the same-named pattern has genuinely different structural properties (different shadcn base component, different usage context). Do NOT flag differences in minor CSS values.

    Write tests in `tests/unit/ui-generator/conflict-detector.test.ts`. No mocking needed — this is a pure function. Create helpers for building existing and new pattern arrays.
