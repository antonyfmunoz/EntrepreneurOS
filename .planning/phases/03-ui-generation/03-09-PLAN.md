# Plan 03-09 — Stitch Screen Management

## Objective

Delete rejected Stitch screens from the project before retry so they don't pollute future generations or count toward project quotas.

## Why

When a screen is rejected at the approval gate (Option 2 — Reject + feedback), the existing pipeline calls Stitch again with revised prompts but leaves the rejected screen sitting in the project. After 3 retries on a single page, a Stitch project can accumulate 4 dead screens, which clutters the UI and skews design memory queries.

## What

1. **Library**: `lib/stitch/screen-management.ts` exporting:
   - `extractScreenIdFromUrl(url)` — pure helper, parses `/screens/{id}/...` from a screenshot URL
   - `deleteScreen(projectId, screenId, mcpInvoke?)` — best-effort, returns `{ deleted, error? }`, never throws
   - `listScreens(projectId, mcpInvoke?)` — best-effort, returns normalised screen records
2. **SKILL.md**: Insert "Screen Cleanup Before Retry" block in Step 3 reject path. Best-effort: any failure logs and continues.
3. **Tests**: 10 vitest cases covering URL parsing edge cases, MCP success/failure, missing inputs.

## Notes

- Stitch MCP does not currently expose `delete_screen` or `list_screens`. The library accepts an injectable `mcpInvoke` so the integration becomes a one-line wiring change once Stitch ships these tools.
- Delete failures are logged with `console.warn` and never block the retry path.

- Reject path in a real run logs "✓ Rejected screen deleted from Stitch" or the explicit "not yet implemented" warning
